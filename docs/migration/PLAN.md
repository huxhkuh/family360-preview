- שרת קיים: `huxhkuh/family360`, ענף `codex/agent-invitations`; נבדק גם העותק המקומי ובו מיגרציות נוספות עד 0021 שטרם נכללו במאגר המרוחק. המקור הועתק ל־`legacy/postgres` ללא שינוי.

- חמישה תפקידים: מנהל, נציג, בעל מקצוע, לקוח, משווק. PostgreSQL המקורי מכיר בארבעה; יש להוסיף סכמת משווקים, הפניות ויומן עמלות.
- לפי תשובת הבעלים בשיחה, ההקמה תהיה בחשבון Cloudflare של יוסי. אין שינוי מסלול חיוב או תעבורת ייצור ללא אישור נוסף.

## סדר ביצוע וקבלה

1. ליצור מלאי RPC וסכמה מול שני המקורות, כולל פערי דמו ומיגרציות מקומיות. קובץ `operation-inventory.json` הוא רשימת מעקב, לא הוכחה להשלמת הסבה.
2. להמיר את הסכמה ל־SQLite/D1: UUID כטקסט, תאריכים ב־UTC, JSON תקין בטקסט, boolean כמספר 0/1, כסף חדש באגורות. לשמר FK, unique, check ואינדקסים; לתרגם במפורש אילוצים שאינם נתמכים.
3. Workers בלבד לקריאות וכתיבות עסקיות. אימות מול Supabase Auth; פרופיל, הרשאות, שיוכים והשבתה נבדקים ב־D1 בכל בקשה. ללא אמון בתפקיד מתוך metadata או בקשת לקוח. פעולות מנהל דורשות aal2.
4. להמיר כל RPC עם בדיקות חיוביות ושליליות; למנוע כתיבות חלקיות ותחרות באמצעות batch אטומי וגרסאות. unknown RPC נחסם.
5. R2 פרטי, גישה דרך Worker אחרי בדיקת מסמך ושיוך. בעל מקצוע מקבל רק מסמך ששותף למשימתו. בדיקת גודל, MIME וחתימת קובץ; גרסאות קבצים נשמרות במפתחות אקראיים חדשים.
6. לחבר את הממשק למתאם שרת נפרד. Supabase משמש Auth בלבד. אין החלפת תפקיד חופשית, קובצי דוגמה, תשלום מדומה או נתוני seed בבניית המערכת האמיתית.
7. סביבת בדיקה נפרדת, משתמשים סינתטיים בלבד. בדיקות API, בידוד משתמשים ותיקים, MFA והשבתה, תהליכים בדפדפן ושחזור גיבוי.
8. לקרוא מהסביבה הקיימת רק מלאי, מונים ומבנה לפני ייצוא. ליצור גיבוי מוצפן מחוץ ל־Git, לבדוק שחזור בסביבה מבודדת ולהכין התאמת מזהי Auth ומסמכים. אין מחיקה של המקור.
9. לאמת את הדומיין, DNS, דואר, HTTPS וכתובת ראשית. לשמר רשומות קיימות, להשתמש ברשימת origins והפניות מדויקת. שינוי Site URL של ייצור יתבצע במסגרת מעבר מאושר בלבד.
10. שער ייצור: כל הפעולות הנדרשות ממומשות ומאומתות, בדיקת שחזור, בדיקות Auth חיות, מחיר ועלויות מוצגים ואישור להעברת התעבורה.

## ממצאי תשתית ראשוניים

נבדק בפועל ב־26.10.2026: כלי Cloudflare MCP פעיל בחשבון שנבחר. הדומיין הראשי ו־www מחוברים ופעילים ב־Pages `family360`. רשומות Resend ו־DMARC קיימות ולא שונו. Supabase בפרויקט `vrswvpvygmjhcarzvuqf` הציג Healthy ו־No backups; שאילתת ספירה מצאה 0 משתמשי Auth, 0 אובייקטים, 3 buckets, ורק automations=2 ו־counters=2 בטבלאות הציבוריות. אין להסיק מכך שהמצב יישאר ריק אחרי הרשמה. Site URL כבר מוגדר לדומיין הראשי; redirect allowlist כולל את הראשי, www ו־family360.pages.dev.

נוצרו משאבי בדיקה בלבד: Pages `mesudarim360-staging`, Worker `mesudarim360-api-staging`, D1 `mesudarim360-staging`, R2 `mesudarim360-documents-staging`. D1 קיבל 4 מיגרציות, בדיקת foreign_key_check נקייה ותרגיל rollback אטומי הצליח בענן. r2.dev כבוי. Worker נפרס; הממשק עדיין לא הועלה: העלאת Pages באמצעות התוסף החזירה 403. המשתמש אישר לפתוח כניסת Wrangler עם account:read, user:read, pages:write; האישור בדפדפן טרם הושלם. נטפרי מחזיר 418 ל־workers.dev החדש; בדיקות HTTP חיות לא אומתו.

בזמן העבודה נוסף במקביל commit של עיצוב דף הבית `7431611`; נשמרו שינוייו. הענף נותר `codex/cloudflare-production-migration`. לפי בקשת המשתמש, הרשמה תיצור לקוח רגיל; הסבה למנהל רק לאחר כניסה ובקשה מפורשת נוספת שלו.
